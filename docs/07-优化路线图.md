# 优化路线图

## P0：提交前必须完成

| 优化项 | 动作 | 收益 | 风险/成本 |
|---|---|---|---|
| Qwen 密钥 | 通过 Sites Secrets 配置并发布 | 补齐 AI 差异化能力 | 需用户安全输入，模型额度未知 |
| 规则核验 | 核对比赛评分、提交格式、截止时间 | 避免无效提交 | 规则尚未提供 |
| 主流程复测 | 单频/双频/unknown/CSV/报告 | 防止发布后回归 | 时间成本低 |
| 公网可用性 | 匿名访问与 Function health | 评委可直接打开 | 已基本完成 |
| 离线兜底 | 固定示例与规则解释 | 网络/AI 故障仍可演示 | 已实现 |

## P1：高收益工程优化

### 1. 计算移入 Web Worker

当前 FFT 与拟合在 UI 主线程执行。大样本可能卡顿。

- 将 `dsp.js` 分析封装到 Worker；
- 主线程只负责进度和图表；
- 加入取消和超时；
- 验收：500,000 样本时页面仍可交互。

### 2. 拆分前端模块

`app.js` 与 `dsp.js` 已超过 500 行。建议：

```text
site/dist/js/
├── core/fft.js
├── core/fit.js
├── core/compare.js
├── core/reliability.js
├── io/csv.js
├── ui/charts.js
├── ui/render.js
└── app.js
```

收益：可测试、可并行开发、降低修改冲突。风险：需要调整静态 import 与测试路径。

### 3. 增加 JavaScript 静态检查

当前只有 Node 测试，没有 ESLint/TypeScript 检查。建议引入：

- ESLint；
- Prettier；
- 可选的 JSDoc + `tsc --checkJs`。

不要在今晚已发布版本上冒险重构；作为下一次发布。

### 4. 模型竞争增强

- 增加模型等价性和参数可辨识证据；
- 残差 ACF 显著性阈值校准；
- 多频间距小于 `1/T` 时明确不可分辨；
- 引入 bootstrap 区间（成本较高）；
- 保持 unknown 拒判。

### 5. 数据导入体验

- CSV 预览表；
- 非均匀检测与解释；
- 多通道选择；
- MAT 与 IQ 只有在对应算法完成后再暴露；
- 明确显示“不支持”，而不是静默忽略。

## P2：架构与产品扩展

### 1. 消除双轨算法风险

浏览器 JS 和 Python 后端各自实现同类模型，长期会漂移。必须先选择主线：

- **方案 A：Sites MVP 主线**，后端只做研究与离线验证；
- **方案 B：完整 Python 产品主线**，Sites 仅展示或调用外部 API；
- **方案 C：共享算法核心**，通过 WASM/服务端统一。

推荐先明确产品目标，再决定，不要同时维护三条链路。

### 2. 数据持久化

当前站点无数据库。若需要保存分析历史：

- 使用 Sites Function backend + 数据库；
- 不做浏览器匿名共享数据库；
- 加入用户身份、所有权、删除和恢复；
- 评估是否真的需要，而不是为了技术展示增加复杂度。

### 3. AM/FM 与通信物理意义

- 实 AM/FM 的可靠参数估计；
- 边带、过调制、瞬时频率质量；
- 相应演示数据与证据；
- 这些能力不能仅凭多频拟合近似宣称。

### 4. 性能与可访问性

- 移动端结果页重新排布；
- Canvas 键盘/文本替代摘要；
- 色弱友好状态；
- 浏览器兼容性测试；
- 大样本图表降采样策略统一。

## 建议执行顺序

1. P0 密钥与规则核验；
2. Worker 化与前端模块拆分；
3. JS 静态检查和回归套件；
4. 明确单一算法主线；
5. 再扩展 AM/FM、MAT、多通道。

## 验收原则

- 任何优化不得降低数值正确性；
- 任何 AI 优化不得允许修改计算结果；
- 任何新格式必须有真实解析和失败测试；
- 线上发布状态、Function 运行和浏览器验证分开记录；
- 不以获奖概率作为工程验收标准。
